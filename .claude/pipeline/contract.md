# Контракт конвейера agent orchestrator

Общие правила для всех агентов конвейера `orchestrator → clarifier → planner → executor → polisher → verifier`.
Каждый субагент конвейера читает этот файл первым шагом (`Read .claude/pipeline/contract.md`), прежде чем
делать что-либо ещё — здесь единственный источник истины для форматов файлов и статусов; сам агент их не
переопределяет и не копирует к себе в изменённом виде.

## Артефакты и именование

- `instructions/REQ-<slug>.md` — файл требований, пишет `clarifier`.
- `instructions/PLAN-<slug>.md` — файл плана, пишет `planner`, дополняют `executor`, `polisher`, `verifier`.
- `<slug>` — kebab-case, задаёт `clarifier` при создании REQ; используется без изменений во всех
  последующих файлах и передаётся между агентами оркестратором.
- `instructions/` в `.gitignore` — это рабочий черновик конвейера, не часть репозитория.

## Статусы

### Статус REQ
- `CLARIFIED` — единственный статус; ставит `clarifier` по завершении интервью.

### Статус PLAN
Последовательность статусов и кто их ставит/ожидает:

| Статус | Ставит | Ожидает на входе |
|---|---|---|
| `PLANNED` | `planner` (нет блокирующих открытых вопросов) | `executor` |
| `BLOCKED` | `planner` (остался хотя бы один `БЛОКИРУЮЩИЙ` вопрос) | `orchestrator` (останавливает конвейер, не запускает `executor`) |
| `IN_PROGRESS` | `executor` (в начале работы) | — (промежуточный статус) |
| `IMPLEMENTED` | `executor` (по завершении) или `polisher` (если остались непочиненные ошибки линта) | `polisher` |
| `POLISHED` | `polisher` (линт/формат/тесты в порядке) | `verifier` |
| `DONE` | `verifier` (PASS) | — (конвейер завершён) |
| `NEEDS_FIXES` | `verifier` (FAIL) | `executor` (ровно один автоматический повторный цикл) |

## Шаблон REQ

```markdown
# Требования: <название задачи>

## Статус
CLARIFIED

## Задача от пользователя (дословно)

## Цель / определение «готово»

## Принятые решения
- <вопрос> → <ответ юзера или вывод из кода, с указанием источника>

## Ограничения и конвенции репозитория

## Открытые вопросы
- [ ] <вопрос> — статус: БЛОКИРУЮЩИЙ | ОТЛОЖЕН — почему

## Вне рамок задачи

## Артефакты
- CONTEXT.md: <обновлён / не требовалось>
- ADR: <путь / не требовалось>
```

## Шаблон PLAN

```markdown
# <Название задачи>

## Статус
PLANNED

## Источники
- Требования: instructions/REQ-<slug>.md
- Baseline: <commit sha> (рабочее дерево на старте: чистое | грязное)

## Цель

## Контекст и решения

## TODO
- [ ] 1. <шаг> — критерий готовности: <проверяемое условие>

## Шаги проверки корректности
- [ ] `npm run verify` проходит (lint + typecheck + test)
- [ ] `npm run compile:test` проходит (прод-сборка компилируется)
- [ ] <функциональные проверки, специфичные для задачи>
- [ ] Изменения соответствуют конвенциям CLAUDE.md

## Открытые вопросы
- [ ] <вопрос> — статус: БЛОКИРУЮЩИЙ | ОТЛОЖЕН — влияние на план

## Вне рамок задачи
```

`## Шаги проверки корректности` всегда стоит сразу после `## TODO` и всегда присутствует. `## Открытые
вопросы` всегда присутствует; если вопросов нет — строка `- нет`.

По ходу конвейера в файл плана дописываются (после `## Вне рамок задачи`, в порядке появления):
- `## Самопроверка executor` — пишет `executor`.
- `## Отчёт polisher` — пишет `polisher`.
- `## Отчёт verifier` — пишет `verifier` (при повторном цикле — второй раздел с тем же заголовком,
  не перезаписывая первый; это единственная история попыток, по которой `orchestrator` считает FAIL).

## Владение разделами плана

| Раздел | Кто пишет / создаёт | Кто отмечает чекбоксы `[x]` |
|---|---|---|
| `## TODO` (состав пунктов) | только `planner` | только `executor` |
| `## Шаги проверки корректности` (состав пунктов) | только `planner` | только `verifier` |
| `## Открытые вопросы` | `planner` (перенос из REQ + свои) | `planner` (закрывает при разборе с юзером) |
| `## Контекст и решения` | `planner`, дополняет `executor` мелкими уточнениями (п. 5 `executor.md`) | — |
| `## Самопроверка executor` | только `executor` | — (не чекбоксы, а отчёт) |
| `## Отчёт polisher` | только `polisher` | — |
| `## Отчёт verifier` | только `verifier` | — |
| `## Статус` (значение) | каждый агент меняет только на выходе из своего шага, см. таблицу статусов выше | — |

`executor` не имеет права добавлять/удалять пункты `## TODO` или менять состав `## Шаги проверки
корректности` — это исключительно зона `planner`.

## Открытые вопросы

Формат строки:
```markdown
- [ ] <вопрос> — статус: БЛОКИРУЮЩИЙ | ОТЛОЖЕН — <влияние на план, если оставить нерешённым>
```

- `БЛОКИРУЮЩИЙ` — пока такой вопрос остаётся открытым (`[ ]`) в файле плана, `orchestrator` не запускает
  `executor`, независимо от статуса плана.
- `ОТЛОЖЕН` — вопрос сознательно не решается сейчас, план на нём не блокируется; влияние на план должно
  быть явно описано в самой строке или в `## Вне рамок задачи`.
- Закрытый вопрос (`[x]`) остаётся в списке с итоговым решением дописанным через ` → `, не удаляется.

## Скиллы

Разрешено вызывать (по ролям — см. каждый `*.md` агента для условий вызова):
- `grilling`, `domain-modeling` — интервью и терминология (`clarifier`).
- `research` — факт из внешней документации вместо вопроса юзеру (`planner`).
- `prototype` — когда вопрос "как это должно выглядеть/вести себя" (`planner`).
- `codebase-design` — форма интерфейса нового модуля (`planner`, `executor`).
- `tdd` — новая логика/эндпоинт реализуется тестами вперёд (`executor`).
- `diagnosing-bugs` — неочевидная причина бага или падения проверки (`executor`, `verifier`).
- `add-nest-module` — TODO-пункт создаёт новый Nest-модуль (`executor`).
- `mattpocock-skills:code-review` — ревью диффа от baseline sha (`verifier`). Указывать именно этим полным
  именем: встроенный скилл `code-review` называется похоже, но не принимает точку отсчёта (baseline commit)
  и не подходит для этой роли.

Запрещено вызывать (не сработает — у скилла `disable-model-invocation: true`, доступен только юзеру как
слэш-команда, а не модели через `Skill`):
- `grill-with-docs` — его тело — это буквально «вызови `grilling` и `domain-modeling`»; агенты вызывают
  эти два скилла напрямую вместо него.
- `wayfinder` — рассчитан на ручной запуск юзером и работу с issue-трекером, а не на планирование одной
  задачи внутри субагента.
