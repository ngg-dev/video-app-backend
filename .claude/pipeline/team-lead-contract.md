# Контракт команды team-lead

Общие правила для всех агентов команды `team-lead → tl-analyst → tl-planner → tl-executor → tl-test-writer →
tl-verifier`. Это отдельная, параллельная команда агентов — не путать с конвейером
`orchestrator → clarifier → planner → executor → polisher → verifier` и его контрактом
(`.claude/pipeline/contract.md`). Артефакты и статусы у команд разные и не пересекаются, чтобы обе команды
можно было использовать на одном репозитории независимо.

Каждый субагент команды читает этот файл первым шагом (`Read .claude/pipeline/team-lead-contract.md`),
прежде чем делать что-либо ещё — здесь единственный источник истины для форматов файлов и статусов; сам
агент их не переопределяет и не копирует к себе в изменённом виде.

## Артефакты и именование

Артефакты команды живут в отдельной подпапке `instructions/team-lead/`, а не вперемешку в `instructions/` —
там же лежат артефакты конвейера `orchestrator` (`REQ-*`/`PLAN-*` без подпапки), и плоский список быстро
становится нечитаемым при накоплении задач обеих команд.

- `instructions/team-lead/REQ-<slug>.md` — файл требований со схемами, пишет `tl-analyst`. В прозе этого и
  других файлов команды он называется «TL-REQ» — это логическое имя артефакта, а не буквальный префикс в
  имени файла (подпапка `team-lead/` уже даёт нужное разделение, дублировать его в имени файла не нужно).
- `instructions/team-lead/PLAN-<slug>.md` — файл плана, пишет `tl-planner`, дополняют `tl-executor`,
  `tl-test-writer`, `tl-verifier`. В прозе — «TL-PLAN», по той же причине.
- `<slug>` — kebab-case, задаёт `tl-analyst` при создании REQ; используется без изменений во всех
  последующих файлах и передаётся между агентами через `team-lead`.
- `instructions/` в `.gitignore` — это рабочий черновик, не часть репозитория; `tl-analyst` создаёт
  `instructions/team-lead/`, если её ещё нет.

## Статусы

### Статус TL-REQ
- `ANALYZED` — ставит `tl-analyst` по завершении обсуждения, если задача требует реализации в коде.
- `ANALYZED_NO_IMPLEMENTATION` — ставит `tl-analyst`, если по итогам обсуждения выяснилось, что реализация
  в коде не требуется (задача чисто аналитическая — достаточно требований и схем). `team-lead` при этом
  статусе завершает работу сразу после `tl-analyst`, не запуская `tl-planner`/`tl-executor`/
  `tl-test-writer`/`tl-verifier`.

### Статус TL-PLAN
Последовательность статусов и кто их ставит/ожидает:

| Статус | Ставит | Ожидает на входе |
|---|---|---|
| `TL_PLANNED` | `tl-planner` (нет блокирующих открытых вопросов) | `tl-executor` |
| `TL_BLOCKED` | `tl-planner` (остался хотя бы один `БЛОКИРУЮЩИЙ` вопрос) | `team-lead` (останавливает работу, не запускает `tl-executor`) |
| `IN_PROGRESS` | `tl-executor` (в начале работы) | — (промежуточный статус) |
| `IMPLEMENTED` | `tl-executor` (по завершении: код готов, `lint`/`format`/`typecheck` чистые) | `tl-test-writer` |
| `TESTED` | `tl-test-writer` (тесты по AAA написаны и проходят) | `tl-verifier` |
| `TL_DONE` | `tl-verifier` (PASS) | — (работа команды завершена) |
| `NEEDS_FIXES` | `tl-verifier` (FAIL, проблема исправима самим `tl-executor` без пересмотра REQ/плана) | `tl-executor` (ровно один автоматический повторный цикл: `tl-executor` → `tl-test-writer` → `tl-verifier`) |
| `REVISION_REQUESTED` | `tl-executor` / `tl-test-writer` / `tl-verifier` (причина проблемы лежит выше их зоны ответственности — REQ/план не бьются с реальностью) | `team-lead` (ведёт диалог с пользователем и выбирает путь — см. «Запрос на ревизию» ниже) |

`REVISION_REQUESTED` и `NEEDS_FIXES` — разные, не перетекающие друг в друга статусы одного и того же
провала: агент выбирает **один** из них по итогам самопроверки/проверки, не оба сразу (см. критерий выбора
в разделе «Запрос на ревизию»).

## Шаблон TL-REQ

```markdown
# Требования: <название задачи>

## Статус
ANALYZED | ANALYZED_NO_IMPLEMENTATION

## Задача от пользователя (дословно)

## Цель / определение «готово»

## Схемы
<mermaid-диаграммы: поток данных, последовательность вызовов, ER — только те, что реально проясняют
задачу; каждая с одной строкой пояснения, что она показывает>

## Принятые решения
- <вопрос> → <ответ юзера или вывод из кода, с указанием источника>

## Ограничения и конвенции репозитория

## Открытые вопросы
- [ ] <вопрос> — статус: БЛОКИРУЮЩИЙ | ОТЛОЖЕН — почему

## Вне рамок задачи

## Артефакты
- CONTEXT.md: <обновлён / не требовалось>
- ADR: <путь / не требовалось>
```

Если по итогам обсуждения `tl-analyst` пересобирает REQ из-за запроса на ревизию (путь A — см. «Запрос на
ревизию» ниже), после `## Артефакты` дописывается (в порядке появления, не перезаписывая предыдущие):

```markdown
## История изменений
### Правка по ревизии N
- Что изменилось: <краткое описание правки REQ/схемы>
- Почему: см. instructions/team-lead/PLAN-<slug>.md → «Запрос на ревизию N»
```

`## История изменений` — это лог **фактических правок** REQ/схемы, отдельный от лога **обсуждения и
решения** («Запрос на ревизию N» в TL-PLAN, см. ниже). Не смешивать: в TL-REQ — что изменилось и почему в
терминах требований, в TL-PLAN — что произошло в диалоге с пользователем и какой путь выбран.

## Шаблон TL-PLAN

```markdown
# <Название задачи>

## Статус
TL_PLANNED

## Источники
- Требования: instructions/team-lead/REQ-<slug>.md
- Baseline: <commit sha> (рабочее дерево на старте: чистое | грязное)

## Цель

## Контекст и решения

## TODO
- [ ] 1. <шаг реализации> — критерий готовности: <проверяемое условие>

## Тесты
- [ ] 1. <сценарий, который должен быть покрыт> — AAA: Arrange <...> / Act <...> / Assert <...>

## Шаги проверки корректности
- [ ] `npm run verify` проходит (lint + typecheck + test)
- [ ] `npm run compile:test` проходит (прод-сборка компилируется)
- [ ] <функциональные проверки, специфичные для задачи>
- [ ] Изменения соответствуют конвенциям CLAUDE.md

## Открытые вопросы
- [ ] <вопрос> — статус: БЛОКИРУЮЩИЙ | ОТЛОЖЕН — влияние на план

## Вне рамок задачи
```

`## Тесты` — это чек-лист сценариев, которые должны быть покрыты тестами (пишет `tl-planner`, по каждому
пункту сразу задаёт форму AAA — что именно arrange/act/assert), а не сами тесты. `## Шаги проверки
корректности` всегда стоит сразу после `## Тесты` и всегда присутствует. `## Открытые вопросы` всегда
присутствует; если вопросов нет — строка `- нет`.

По ходу работы в файл плана дописываются (после `## Вне рамок задачи`, в порядке появления):
- `## Отчёт executor` — пишет `tl-executor` (что реализовано, результат lint/format/typecheck).
- `## Отчёт test-writer` — пишет `tl-test-writer` (какие тесты добавлены, результат прогона).
- `## Отчёт verifier` — пишет `tl-verifier` (при повторном цикле — второй раздел с тем же заголовком, не
  перезаписывая первый; это единственная история попыток, по которой `team-lead` считает FAIL).
- `## Запрос на ревизию N` — пишет инициатор (`tl-executor`/`tl-test-writer`/`tl-verifier`), дополняет
  `team-lead` решением пользователя и выбранным путём (см. «Запрос на ревизию» ниже). `N` — порядковый
  номер (1, 2, ...; в текущей версии команды возможен только один запрос за прогон, но нумерация всё равно
  используется для однозначной связи с `## История изменений` в TL-REQ).

## Владение разделами плана

| Раздел | Кто пишет / создаёт | Кто отмечает чекбоксы `[x]` |
|---|---|---|
| `## TODO` (состав пунктов) | только `tl-planner` | только `tl-executor` |
| `## Тесты` (состав пунктов) | только `tl-planner` | только `tl-test-writer` |
| `## Шаги проверки корректности` (состав пунктов) | только `tl-planner` | только `tl-verifier` |
| `## Открытые вопросы` | `tl-planner` (перенос из TL-REQ + свои) | `tl-planner` (закрывает при разборе с юзером) |
| `## Контекст и решения` | `tl-planner`, дополняют `tl-executor`/`tl-test-writer` мелкими уточнениями | — |
| `## Отчёт executor` | только `tl-executor` | — (не чекбоксы, а отчёт) |
| `## Отчёт test-writer` | только `tl-test-writer` | — |
| `## Отчёт verifier` | только `tl-verifier` | — |
| `## Запрос на ревизию N` (проблема + рекомендуемый путь) | только агент-инициатор | — |
| `## Запрос на ревизию N` (решение пользователя + выбранный путь + отметка «Возобновлено») | только `team-lead` | — |
| `## Статус` (значение) | каждый агент меняет только на выходе из своего шага, см. таблицу статусов выше | — |

`tl-executor` не имеет права добавлять/удалять пункты `## TODO` или `## Тесты` — состав обоих чек-листов
исключительно зона `tl-planner`. `tl-test-writer` не имеет права добавлять/удалять пункты `## TODO` или
менять состав `## Тесты` — только отмечать чекбоксы `## Тесты` и писать сами тесты в коде.

## Открытые вопросы

Формат строки:
```markdown
- [ ] <вопрос> — статус: БЛОКИРУЮЩИЙ | ОТЛОЖЕН — <влияние на план, если оставить нерешённым>
```

- `БЛОКИРУЮЩИЙ` — пока такой вопрос остаётся открытым (`[ ]`) в файле плана, `team-lead` не запускает
  `tl-executor`, независимо от статуса плана.
- `ОТЛОЖЕН` — вопрос сознательно не решается сейчас, план на нём не блокируется; влияние на план должно
  быть явно описано в самой строке или в `## Вне рамок задачи`.
- Закрытый вопрос (`[x]`) остаётся в списке с итоговым решением дописанным через ` → `, не удаляется.

## Запрос на ревизию

Механизм для случая, когда `tl-executor`/`tl-test-writer`/`tl-verifier` в процессе работы обнаруживает, что
проблема не в их зоне ответственности, а в предпосылках, заложенных `tl-analyst` или `tl-planner` (REQ,
схема или план не бьются с реальностью кода) — то есть чинить это на своём уровне бессмысленно. Отличие от
`БЛОКИРУЮЩИЙ` открытого вопроса: тот виден **до** старта `tl-executor` (ворота team-lead), запрос на
ревизию — проблема, вскрывшаяся **в процессе** работы.

### Критерий: ревизия или локальная доработка

Агент решает сам, к какой из категорий относится найденная проблема:
- **Локальная** (решает сам, без ревизии) — мелкая деталь реализации/теста, не меняющая суть решения из
  TL-REQ/TL-PLAN. Фиксируется в `## Контекст и решения` как обычно.
- **Исправимо `tl-executor`, но не прямо сейчас** (`tl-verifier` → `NEEDS_FIXES`) — код/тесты не
  реализуют то, что требует TODO/сценарий, но само требование или план корректны — обычная доработка по
  существующему циклу retry.
- **Запрос на ревизию** (`REVISION_REQUESTED`) — причина лежит выше: сама формулировка требования, схема
  или декомпозиция плана не соответствуют тому, что должно быть. Продолжать реализацию/тесты/проверку по
  текущему TL-REQ/TL-PLAN бессмысленно, пока это не пересмотрено с пользователем.

### Формат сигнала

Агент-инициатор:
1. Дописывает в конец TL-PLAN раздел (следующий свободный `N`, начиная с 1):
   ```markdown
   ## Запрос на ревизию N
   - Инициатор: tl-executor | tl-test-writer | tl-verifier
   - Проблема: <что именно не бьётся с TL-REQ/TL-PLAN/схемой, конкретно>
   - Рекомендуемый путь: A — пересобрать требования и схему (tl-analyst) | B — скорректировать план
     (tl-planner) | C — продолжить с уточнением, без пересборки файлов
   - Обоснование рекомендации: <почему именно этот путь>
   ```
2. Ставит статус плана `REVISION_REQUESTED`.
3. Завершает работу — сам не вызывает `tl-analyst`/`tl-planner`, не ведёт диалог с пользователем, это
   делает `team-lead`.

### Диалог и маршрутизация (ведёт `team-lead`)

1. `team-lead` читает `## Запрос на ревизию N`, ретранслирует пользователю проблему через `AskUserQuestion`
   с явным выбором пути (рекомендация агента — первый вариант, с пометкой «Рекомендую»):
   - **Путь A** — пересобрать требования и схему (`tl-analyst`)
   - **Путь B** — скорректировать только план (`tl-planner`, без `tl-analyst`)
   - **Путь C** — продолжить с уточнением, без пересборки файлов
2. Дописывает в тот же раздел `## Запрос на ревизию N`:
   ```markdown
   - Решение пользователя: <кратко>
   - Путь: A | B | C
   ```
3. Маршрутизирует:
   - **Путь A** — запускает `tl-analyst` с путями к TL-REQ/TL-PLAN и номером ревизии N. `tl-analyst`
     проводит точечное (не с нуля) обсуждение вокруг найденной проблемы, обновляет TL-REQ на месте (раздел
     `## Схемы` и связанные), дописывает `## История изменений` со ссылкой на ревизию N. Затем `team-lead`
     запускает `tl-planner` как обычно (полный проход планирования по обновлённому TL-REQ), а дальше —
     обычный порядок работы начиная с ворот открытых вопросов и `tl-executor`.
   - **Путь B** — запускает `tl-planner` напрямую (TL-REQ не трогается), передав номер ревизии N и текст
     проблемы. `tl-planner` корректирует состав `## TODO`/`## Тесты`/`## Шаги проверки корректности`
     точечно, не переписывая план с нуля. Дальше — обычный порядок начиная с ворот открытых вопросов и
     `tl-executor`.
   - **Путь C** — дописывает решение пользователя в `## Контекст и решения`, отмечает раздел `## Запрос на
     ревизию N` строкой `- Возобновлено`, ставит статус плана на тот, что предшествовал старту
     агента-инициатора в этом прогоне (`tl-executor` → `TL_PLANNED`; `tl-test-writer` → `IMPLEMENTED`;
     `tl-verifier` → `TESTED`), и запускает **того же агента**, который инициировал запрос (не обязательно
     `tl-executor`) — тот продолжает с места, на котором остановился, учитывая заметку.

### Лимит

Не более **одного запроса на ревизию за весь прогон** — отдельный счётчик от лимита «1 retry после FAIL
verifier» (считаются они независимо: количество разделов `## Запрос на ревизию N` — для ревизий, количество
FAIL-разделов `## Отчёт verifier` — для retry). Если в файле уже есть раздел `## Запрос на ревизию 1` и
приходит второй запрос — `team-lead` **не** открывает новый раунд `AskUserQuestion`, останавливает работу и
сообщает об этом пользователю напрямую текстом (см. `team-lead.md`).

### Как агент определяет, что это возобновление, а не первый запуск/доработка

Перед тем как решить «первый запуск / доработка после FAIL / возобновление после ревизии» (см. каждый
`*.md` агента), агент проверяет в этом порядке:
1. Есть ли `## Запрос на ревизию N`, где я — инициатор, с отметкой `- Возобновлено`, но без более позднего
   собственного отчёта после этой отметки? → это возобновление: не переделывай всё с нуля, продолжи с
   места остановки, учитывая заметку в `## Контекст и решения`.
2. Иначе — обычная логика «первый запуск / доработка после FAIL» (без изменений).

## Тесты и методология AAA

`tl-test-writer` пишет тесты только после того, как `tl-executor` реализовал функциональность (тесты
пишутся после кода, не в стиле TDD/red-green — это сознательное решение этой команды). Каждый тест должен
явно разделяться на три секции с комментариями `// Arrange`, `// Act`, `// Assert` (или пустой строкой
между блоками, если стиль файла уже задаёт такое разделение) — один тест проверяет одно поведение, без
смешения нескольких сценариев в одном `it`/`test`.

## Скиллы

Разрешено вызывать (по ролям — см. каждый `*.md` агента для условий вызова):
- `grilling`, `domain-modeling` — интервью и терминология (`tl-analyst`).
- `research` — факт из внешней документации вместо вопроса юзеру (`tl-planner`).
- `prototype` — когда вопрос "как это должно выглядеть/вести себя" (`tl-planner`).
- `codebase-design` — форма интерфейса нового модуля (`tl-planner`, `tl-executor`).
- `diagnosing-bugs` — неочевидная причина бага или падения проверки (`tl-executor`, `tl-test-writer`,
  `tl-verifier`).
- `add-nest-module` — TODO-пункт создаёт новый Nest-модуль (`tl-executor`).
- `mattpocock-skills:code-review` — ревью диффа от baseline sha (`tl-verifier`). Указывать именно этим
  полным именем: встроенный скилл `code-review` называется похоже, но не принимает точку отсчёта (baseline
  commit) и не подходит для этой роли.

Запрещено вызывать `tdd` (плагин `mattpocock-skills`) в этой команде — он реализует тесты-вперёд
(red-green-refactor), а эта команда осознанно пишет тесты после кода отдельным агентом (`tl-test-writer`).
Если нужен конвейер с TDD — используйте существующую команду `orchestrator → clarifier → planner → executor
→ polisher → verifier`, там `executor` вызывает `tdd` сам.

Запрещено вызывать (не сработает — у скилла `disable-model-invocation: true`, доступен только юзеру как
слэш-команда, а не модели через `Skill`):
